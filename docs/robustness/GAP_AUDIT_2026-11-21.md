## 5. Invariant gaps found and addressed locally

The baseline Store guarded CAS and terminal immutability but allowed arbitrary changes between nonterminal states. The new graph blocks reverse progress and cancellation reversal even if a caller supplies broad expected states. Previously permissive JSON decoding also accepted duplicate names, case aliases, null/default substitutions and malformed UTF-8 replacements; the API now rejects these ambiguous requests before admission. These are bounded local correctness changes, not a claim of a completed security assessment.

## 6. Deviations and corrections to the proposed plan

- **C1/C6:** preserve existing wire states and idempotency fingerprints in this iteration. `queued` represents durable admission; rejected submissions are HTTP outcomes; timeouts still end `failed`. A versioned reason-code/state migration is needed before adding `timed_out`, `submitted`, `admitted` or persisted rejection records. Every terminal record can be immutable without guaranteeing that a permanently unavailable cluster or lost store will eventually produce one.
- **C5/C7:** repair only resources with verified ownership and preconditions. Missing activated work must not be replayed automatically, stray resources must not be silently adopted, and deletion cannot fence an unreachable physical worker. Scope any cancellation latency bound to observed, healthy infrastructure and a declared test environment.
- **C8/R5/R6:** do not enable infrastructure retries before an external-effect contract exists. A local journal alone cannot make a remote write exactly once: the provider needs idempotency/reconciliation and stale attempts need fencing. Ambiguous writes remain unknown. A snapshot cannot undo an email or database write; cancellation and compensation are different operations, and compensation may fail.
- **C11/P6:** HA is requested in phase 0 while availability/rollback is assigned to phase 6. The current exclusive bbolt lock, one replica and Recreate deployment require maintenance windows. Leader election alone cannot make that storage shared or provide zero downtime. Resolve the distributed store/migration/ownership design before promising HA; do not scale this deployment to two replicas.
- **S1/S2/S3:** profiles currently belong to the API/backend, not individual templates, and Kata is unsupported. PID bounds require node configuration. Resource, deadline and termination limits need node-level observation. Metadata, node-local paths and Nitro vsock remain explicit qualification targets.
- **N1/N2/N5/N7:** keep phase 1 offline/default deny. Network failure alone is not isolation proof: use reachable positive controls and cover startup, additive policy, applicable address families and node-local routes. A no-key scan with no successful brokered call does not qualify credential handling. Five-second revocation must distinguish future decisions from in-flight effects and define fail-closed behavior under partitions.
- **Nitro / gateway:** Nitro support already includes NIC removal, memory scratch, placement, overhead checks and protected annotations; it is more than a RuntimeClass substitution. The current NIC-free profile cannot reach a future gateway. A network-capable profile needs an explicit design and new qualification; do not silently toggle the annotation.
- **B2/O4:** strict reservation counts do not imply an exact provider-dollar cap. Price versions, conservative maximum request reservations, settlement, failed/unknown calls and billing tolerance need definitions. Fixed-node headroom is not a reduced AWS bill.
- **Phase 3:** the new proposal suggests 20% cost or 50% fewer operator steps, while the existing example protocol uses 20% cost or 25% lower median operator time. Steps and elapsed time are distinct metrics. Keep existing evidence registrations intact; choose and register the future metric/threshold before collection rather than silently changing the evaluator.
- **Phase ordering:** preserve the plan's upstream-first direction. Gateway spikes and new drivers wait for the preceding qualified phase. Cluster preparation is a prerequisite for EKS exit tests; a completed local audit does not satisfy them. Existing evaluation tools do not establish feature exclusivity or a commercial advantage.
